Demo Maker is a tool that automates the creation of recorded product demonstrations — it takes presentation slides, synthesised speech, and supporting assets and assembles them into a finished video...
Version 0.1.4 delivers three improvements that make the tool leaner, more reliable, and easier to operate in a consistent way...

Let's start with PDF page generation and dependency reduction...
Previously, the tool relied on a separate command called split-pdf, whose sole job was to take a PDF presentation and break it apart into individual image pages — one per slide...
To do that, we depended on a third-party system package called poppler-utils, which had to be bundled into our Docker image...
Docker images are self-contained environments that package an application with everything it needs to run; the larger the image, the slower it is to distribute and deploy...
We discovered that Marp — the tool we already use to generate the PDF from slides — is also capable of producing those individual page images directly...
This meant the split-pdf command and the poppler-utils dependency were no longer needed, and both have been removed...
The result is a smaller Docker image, which reduces deployment time and removes a maintenance burden we no longer need to carry...

Next, let's cover the build reliability fix...
The build command is responsible for taking all processed assets and delivering a final merged file to a designated output folder...
An issue was identified where this final copy step did not always complete, meaning the output file never arrived at its destination...
Alongside that, a temporary working folder — used internally during the merge process — was not being cleaned up, leaving leftover files after each run...
Both issues have been resolved...
The final file is now reliably delivered to the correct destination, and the temporary folder is removed once the build completes...
In day-to-day operation this means builds are trustworthy — the output you expect is where you expect it, every time...

Now let's look at audio normalisation...
TTS, Text-To-Speech, synthesis tools are sensitive to the format of any reference audio provided to them — they expect audio to have a single channel, known as mono, and a specific sample rate of 24 kilohertz...
If reference audio arrives in a different format, the synthesis step can produce degraded or inconsistent results...
A new command has been added to the tool that takes a reference audio file and normalises it automatically — converting it to mono and setting the sample rate to 24 kilohertz...
This removes a manual preparation step that was previously left to the operator, and ensures the TTS stage always receives audio in the correct format...
